# بازبینی مهندسی و وضعیت رگرسیون

این سند، بازبینی ایستای مخزن را در شاخهٔ `main` در commit
`59941cabfa07431a3b3c36500131e221d164569e` خلاصه می‌کند. این بازبینی جایگزین
اجرای تست‌ها، بررسی خروجیِ زنده یا ممیزی امنیتی نیست.

## تغییرات مهندسی

- workflow مستقل `regression.yml` افزوده شده تا Pull Requestهای هدف‌گرفته به
  `main` پیش از ادغام، با Python 3.12 بررسی شوند.
- اکشن‌های workflow با SHA کامل pin شده‌اند.
- workflow وابستگی‌های pin‌شده را نصب می‌کند، فایل‌های Python در `scripts/` و
  `src/` را compile می‌کند و مجموعهٔ رگرسیون موجود را اجرا می‌کند.
- مجوز workflow فقط `contents: read` است؛ آزمون‌ها از workflow تولید و انتشار
  جدا هستند.

## نکتهٔ مهم دربارهٔ زمان‌بندی

در `aggregate.yml`، cron فعلی روی دقیقه‌های ۱۵ و ۴۵ هر ساعت تنظیم شده است، یعنی
هر ۳۰ دقیقه اجرا می‌شود؛ `UPDATE_INTERVAL_MINUTES` و `AGG_UPDATE_INTERVAL_MIN`
نیز ۳۰ هستند و freshness gate برابر ۲۵ دقیقه است. توضیحات بالای workflow و
READMEهای موجود هنوز از ۴۵ دقیقه و دروازهٔ ۴۰ دقیقه می‌گویند و با تنظیم اجرایی
نمی‌خوانند. تا زمان تصمیم مالک، تنظیم واقعی workflow مرجع است: **۳۰ دقیقه / ۲۵
دقیقه**.

## اعتبارسنجی و محدودیت نتیجه

L3 عمداً `continue-on-error` دارد تا اختلال شبکهٔ runner انتشار دسته‌های پایه
را متوقف نکند. بارگذاری واقعی subscription در mihomo نیز به‌طور پیش‌فرض هشدار
می‌دهد، نه اینکه انتشار را ببندد. بنابراین سبز بودن انتشار به‌تنهایی به معنای
موفقیت این دو کنترل نیست؛ باید خلاصهٔ run و `validation.json` را نیز بررسی کرد.

Workflow تازهٔ regression را هنوز GitHub Actions اجرا نکرده است. تا آن run
تمام نشود، **رگرسیون تأییدشده نیست**. این سند هیچ ادعایی دربارهٔ تست اجراشده یا
صفر بودن خطاها نمی‌کند.

## پیشنهادهای بعدی

1. زمان‌بندی را در یک منبع حقیقت نگه دارید و هر دو README را با آن هماهنگ کنید.
2. نتیجهٔ L3 و subscription validation را در خلاصهٔ run آشکارا از نتیجهٔ انتشار
   جدا کنید و برای شکست‌های مکرر هشدار مستقل بگذارید.
3. در ادامه، تست‌ها را از `scripts/test_pipeline.py` بزرگ به ماژول‌های موضوعی
   تقسیم کنید و برای هر بخش مدت اجرا و وضعیت اجرا/skip را ثبت کنید.
4. schema/version برای `index.json` و `health.json` تعریف کنید تا تغییر قرارداد
   مصرف‌کننده‌های پنل را ناخواسته نشکند.
5. به‌روزرسانی Python و باینری‌های کلاینت را دوره‌ای انجام دهید، اما فقط با
   آزمون مقایسه‌ای و بررسی checksum.
